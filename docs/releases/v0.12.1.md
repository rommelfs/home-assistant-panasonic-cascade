# 0.12.1 — Repeated ESPHome temperature reports

Experimental prerelease.

PV charging could repeatedly reset its stable-surplus timer when Home Assistant suppressed identical ESPHome sensor packets before updating `last_reported`. For the configured ESPHome buffer sensor, Cascade now observes matching temperature packets on the existing API connection. It neither creates another connection nor requests/replays cached values, changes firmware, patches HA, or republishes the source state.

The first matching packet after binding is ignored because it can be a subscription snapshot. Subsequent packets carry their actual receipt time and temperature into the existing measurement validation. Missing/NaN/out-of-range values, silence beyond the configured maximum age, lost connections and the temperature stop limit still block or end charging. Source/connection changes and unload remove the observer. Unsupported ESPHome runtime layouts block charging rather than relaxing freshness. Other source platforms retain the usual HA report checks.

PV charge status attributes `temperature_native_packets` and `temperature_native_report_age_s` help distinguish a stable temperature from a device that stopped reporting. Integration receipt confirms a device report, not independent physical probe calibration.

The adapter uses bounded private HA/ESPHome runtime access; compatibility must be checked when upgrading those components. Reflash the sensor with regular unfiltered measurements and `force_update: true` if the device itself stops publishing unchanged measurements. No cached-value heartbeat can provide missing measurements.

No changes to the 1,000 W battery reserve, surplus thresholds, 0–10 °C offset limits, heating curve, or dashboard layout.
